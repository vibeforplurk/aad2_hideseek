# 一、專案概述

## 1.1 專案目的

本專案旨在製作一個協助主持人管理《暮影領地捉迷藏》遊戲流程的網頁工具。

遊戲實際進行仍以 Plurk 為主要場域，主持人透過 Plurk 與玩家互動、公布遊戲結果及擲骰。

輔助網站不需要提供玩家登入、即時連線或多人共同操作功能，而是由主持人單獨使用，負責：

- 管理遊戲狀態與角色位置。
- 計算角色移動路徑與移動結果。
- 判定設施事件、途經效果及捕獲條件。
- 生成可直接複製至 Plurk 的遊戲敘述。
- 顯示遊戲地圖及角色移動情況。
- 保存遊戲進度，並支援手動匯入與匯出。

## 1.2 核心設計原則

1. **主持人單人操作**：所有遊戲狀態均由主持人輸入及確認。
2. **Plurk 負責玩家互動**：網站不直接與玩家溝通，也不需要串接 Plurk API。
3. **骰子結果手動輸入**：玩家仍使用 Plurk 原有的擲骰方式，主持人將結果輸入網站。
4. **公開資訊一致**：網站生成的地圖及文字均以可公開給所有玩家的資訊為準。
5. **不依賴後端**：遊戲資料暫存於主持人使用的瀏覽器。
6. **操作結果可追溯**：重要操作應能撤銷，並保留必要的操作紀錄。
7. **保留人工裁定空間**：特殊情況由主持人決定，不應強迫所有遊戲狀況都由程式自動處理。

# 二、技術架構

## 2.1 技術選擇

本專案採用純前端架構。

| 項目 | 技術 | 用途 |
|---|---|---|
| 網頁結構 | HTML | 頁面及操作介面 |
| 視覺樣式 | CSS | 版面、按鈕、面板及地圖呈現 |
| 程式邏輯 | JavaScript | 遊戲流程、移動計算、事件判定 |
| 地圖顯示 | SVG | 角色位置、路徑及地圖標記 |
| 資料暫存 | LocalStorage | 保存瀏覽器中的遊戲狀態 |
| 資料備份 | JSON | 匯入、匯出遊戲進度 |
| 圖片輸出 | SVG → PNG | 匯出可發布至 Plurk 的地圖 |

不需要使用：

- Flask 或其他後端框架。
- SQLite 或其他資料庫。
- 使用者帳號與登入系統。
- 雲端即時同步。
- WebSocket 或即時通訊服務。

網站可部署於 GitHub Pages 等靜態網站服務。

## 2.2 資料保存方式

使用 LocalStorage 保存遊戲狀態。

LocalStorage 的特性：

- 關閉瀏覽器後仍可保留資料。
- 不需要伺服器即可使用。
- 同一網站來源、同一瀏覽器可以讀取原有資料。
- 清除網站資料時，遊戲進度也可能一併消失。
- 不會自動同步至其他裝置或瀏覽器。

因此網站必須提供 JSON 匯出與匯入功能，作為備份及跨裝置轉移方式。

不建議使用 Cookie 保存遊戲資料。

# 三、網站功能規劃

網站以主持人控制台為核心，建議分為以下五個主要功能區。

## 3.1 遊戲管理

負責建立、設定及載入遊戲。

### 必要功能

- 建立新遊戲。
- 選擇遊戲模式。
  - 1V1 模式。
  - 多人模式。
- 設定玩家名稱。
- 設定異常／追捕者名稱。
- 設定初始位置。
- 設定目前回合數。
- 設定最大回合數。
- 查看目前遊戲狀態。
- 清除目前遊戲並重新開始。

### 手動接續遊戲

提供手動輸入遊戲狀態的功能，讓主持人可以在沒有原始存檔的情況下繼續遊戲。

需要輸入的資料包括：

- 遊戲模式。
- 目前回合數。
- 最大回合數。
- 所有角色的位置。
- 角色是否仍在遊戲中。
- 特殊狀態及效果。
- 目前行動角色。
- 目前行動階段。
- 已經發生的特殊事件。
- 尚未完成的移動資訊。

如果目前處於移動階段，還需要輸入：

- 原始移動步數。
- 移動方向。
- 已移動步數。
- 剩餘步數。
- 已觸發的途經效果。
- 目前移動路徑。

系統應在套用資料前檢查必要欄位是否完整，避免不完整的遊戲狀態造成後續計算錯誤。

## 3.2 地圖管理

負責顯示遊戲地圖及角色位置。

目前已有地圖底圖素材，開發時應以既有底圖為基礎，不另外重製地圖美術。

### 必要功能

- 顯示完整 20 格地圖。
- 顯示各設施名稱及位置。
- 顯示所有角色目前所在位置。
- 區分不同角色的地圖標記。
- 顯示角色移動前的位置。
- 顯示角色移動後的位置。
- 顯示本次移動路徑。
- 顯示移動方向。
- 顯示特殊移動效果，例如傳送或額外移動。

### 地圖顯示模式

建議提供兩種模式：

**A. 遊戲狀態地圖**

顯示目前遊戲的整體狀況：

- 所有角色目前位置。
- 目前回合數。
- 角色存活狀態。
- 必要的特殊標記。

**B. 移動過程地圖**

顯示單次行動的移動過程：

- 移動起點。
- 移動終點。
- 經過的格子。
- 移動方向。
- 途經設施。
- 特殊移動或傳送路徑。

### 地圖匯出

提供 PNG 匯出功能。

匯出的圖片應：

- 保留地圖底圖。
- 保留角色標記及位置。
- 保留必要的移動路徑與方向。
- 不包含主持人操作按鈕。
- 不包含不需要公開的操作面板。
- 具備適合 Plurk 貼文的尺寸及清晰度。

另提供「圖片預覽模式」，讓主持人能在匯出前確認圖片內容。

## 3.3 事件與行動管理

這是整個網站最重要的遊戲邏輯功能。

系統應依照目前角色、所在設施及遊戲階段，提供對應的事件選項與判定。

### 行動流程

每位角色的行動應依序處理：

1. 事件階段。
2. 移動階段。
3. 途經判定。
4. 停留位置判定。
5. 回合結束或進入下一位角色。

系統應明確顯示目前階段，避免主持人跳過尚未完成的判定。

### 骰子輸入

所有骰子結果由主持人手動輸入。

輸入介面應依目前判定需求提供相應欄位，例如：

- dice20。
- dice6。
- dice4。
- draw 吉／凶。
- coin：P／骨／特殊結果。

骰子結果應進行合法性檢查，例如 dice4 只能輸入 1～4。

若判定需要多次擲骰，應能依序輸入並保留每次結果。

### 事件處理

系統依照角色目前所在設施，顯示對應事件。

例如：

- 黑薔薇莊園：事件步數減少，並設定下回合的事件限制。
- 血月裁決：依照角色及骰運產生額外效果。
- 旋轉木馬：改變移動步數及途經規則。
- 茶館：使用 dice6 決定移動步數，並提供拒絕途經的選項。
- 飛天試煉：依照骰運決定是否傳送至其他設施。
- 古堡探險：依照骰運決定是否跳過移動判定。
- 三明治男爵：提供額外移動。
- 幽影海盜船：依照骰運決定移動方向。

事件處理應採用可擴充的設施設定，不應將所有設施判定集中寫在同一個大型函式中。

### 途經判定

當角色移動經過設施格時，系統應依照該設施的途經效果進行判定。

必要功能：

- 自動辨識移動路徑中的設施。
- 依規則判斷是否觸發途經效果。
- 需要擲骰時提示主持人輸入結果。
- 計算途經效果造成的步數變化。
- 支援方向反轉。
- 支援剩餘步數取消。
- 支援額外移動。
- 記錄本次行動已觸發的途經效果。

一般規則為：經過複數設施時，只觸發第一個符合條件的途經設施；但特殊設施或效果若另有規定，應以個別規則為準。

### 移動計算

系統依照主持人輸入的骰子結果計算移動。

必要功能：

- 選擇移動方向。
- 輸入移動步數。
- 計算移動終點。
- 記錄移動路徑。
- 判斷經過哪些設施。
- 處理途經效果造成的移動變化。
- 支援額外移動。
- 支援反方向移動。
- 支援傳送。
- 顯示最終位置。

移動計算應以 20 格循環地圖為基礎。

### 捕獲判定

系統應依照遊戲模式與目前階段判斷是否發生捕獲。

1V1 模式需要處理：

- 追捕者停留在躲藏者位置。
- 追捕者途經躲藏者位置。
- 躲藏者停留在追捕者位置。
- 躲藏者途經追捕者位置。
- 特殊設施造成的捕獲或移動取消。

多人模式需要額外處理：

- 多位躲藏者同時位於同一格。
- 躲藏者抵達順序。
- 追捕者捕獲目標的選擇。
- 特殊事件指定捕獲最近的躲藏者。
- 躲藏者被捕獲後的退場狀態。
- 接待廳的返場機制。

所有捕獲結果應在主持人確認後才正式套用。

## 3.4 Plurk 文字生成

系統應依照目前遊戲階段，生成可以直接複製到 Plurk 的文字。

### 必要功能

- 依照目前行動階段生成文字。
- 依照設施生成事件敘述。
- 依照移動結果生成移動敘述。
- 依照途經結果生成途經敘述。
- 依照捕獲結果生成判定敘述。
- 提供文字預覽。
- 提供一鍵複製。

### 文字生成原則

網站負責整理遊戲結果，不需要自動生成大量自由敘事。

應優先採用可編輯的文字模板，讓主持人可以自行調整敘述風格。

模板可使用以下變數：

- `{round}`：目前回合。
- `{player_name}`：玩家名稱。
- `{character_name}`：角色名稱。
- `{facility_name}`：設施名稱。
- `{start_position}`：起始位置。
- `{end_position}`：最終位置。
- `{movement_steps}`：移動步數。
- `{movement_direction}`：移動方向。
- `{event_result}`：事件結果。
- `{judgment_result}`：判定結果。

例如：

「第 {round} 回合，{player_name} 抵達了 {facility_name}。本次事件結果為：{event_result}。」

### 重要設計

文字預覽與遊戲狀態更新必須分開。

主持人可以先生成、修改及複製文字，但只有在確認套用結果後，才正式改變遊戲狀態。

避免因為單純預覽文字，就意外推進回合或改變角色位置。

## 3.5 遊戲資料管理

### 自動暫存

每次主持人確認重要操作後，自動將完整遊戲狀態保存至 LocalStorage。

### 手動保存

提供手動保存功能，讓主持人可以在重要階段建立存檔。

### JSON 匯出

將目前完整遊戲狀態匯出為 JSON 檔案。

### JSON 匯入

讀取既有 JSON 檔案，還原遊戲狀態。

匯入時應檢查資料格式及版本，避免讀取錯誤或不相容的存檔。

### 操作紀錄

記錄重要遊戲操作，例如：

- 角色移動。
- 設施事件。
- 途經判定。
- 角色捕獲。
- 角色返場。
- 回合推進。
- 特殊狀態變更。

### 撤銷操作

提供撤銷功能。

撤銷時應還原完整遊戲狀態，而不只是角色位置。

例如角色移動後觸發設施效果，撤銷時應一併還原：

- 角色位置。
- 移動步數。
- 特殊效果。
- 回合數。
- 角色存活狀態。
- 已觸發的事件紀錄。

# 四、遊戲規則資料結構

## 4.1 地圖設施資料

20 格地圖應以資料方式定義，而不是將設施規則直接寫死在地圖顯示程式中。

每個設施至少需要：

- 格子編號。
- 設施名稱。
- 設施類型。
- 事件規則。
- 途經規則。
- 是否需要擲骰。
- 是否會改變移動步數。
- 是否會改變角色狀態。

建議將設施規則獨立存放於 `facilities.js`。

## 4.2 角色資料

每個角色應至少保存：

- 角色 ID。
- 角色名稱。
- 角色類型。
- 目前位置。
- 是否仍在遊戲中。
- 是否被捕獲。
- 是否具有特殊狀態。
- 特殊狀態持續時間。
- 返場次數（多人模式）。

多人模式還需要記錄躲藏者的抵達順序。

## 4.3 遊戲狀態

遊戲狀態應由一份統一資料管理。

建議包含：

```javascript
const gameState = {
  version: 1,

  mode: "1v1",

  round: 1,
  maxRound: 10,

  phase: "event",

  activePlayerId: null,

  players: [],

  movement: {
    steps: 0,
    remainingSteps: 0,
    direction: null,
    path: [],
    triggeredFacilities: []
  },

  logs: [],

  settings: {}
};
```

以上僅為初始資料結構示意，實際欄位需依照完整遊戲規則擴充。

所有功能均應讀取及更新同一份 `gameState`。

不得讓地圖、事件生成器、移動計算及存檔系統各自保存互不相通的角色位置或遊戲進度。

# 六、操作介面規劃

建議採用單一控制台介面，避免主持人頻繁切換頁面。

## 6.1 主畫面配置

建議分成三個主要區域：

### 左側：遊戲資訊

顯示：

- 遊戲模式。
- 目前回合。
- 最大回合。
- 目前行動角色。
- 目前行動階段。
- 所有角色目前位置。
- 角色存活狀態。

### 中央：遊戲地圖

顯示：

- 地圖底圖。
- 角色位置。
- 移動路徑。
- 起點與終點。
- 特殊效果標記。

### 右側：操作面板

依照目前階段顯示不同內容：

- 事件選擇。
- 骰子結果輸入。
- 移動方向選擇。
- 途經判定。
- 捕獲判定。
- 文字預覽。
- 複製 Plurk 文字。
- 確認套用結果。

## 6.2 操作流程範例

以躲藏者在設施格開始行動為例：

1. 系統辨識目前行動角色及所在設施。
2. 顯示該設施的事件內容。
3. 主持人輸入所需骰子結果。
4. 系統計算事件結果。
5. 主持人確認事件效果。
6. 系統進入移動階段。
7. 主持人輸入移動步數及方向。
8. 系統顯示預計移動路徑。
9. 若經過設施，系統提示途經判定。
10. 主持人輸入途經骰運。
11. 系統計算最終移動結果。
12. 系統顯示角色新位置及捕獲判定。
13. 主持人確認套用結果。
14. 系統更新地圖及遊戲狀態。
15. 生成可複製至 Plurk 的文字。

實際流程應依照各設施特殊規則調整。

# 七、遊戲規則實作原則

## 7.1 1V1 模式

遊戲基本設定：

- 地圖共 20 格。
- 躲藏者與追捕者各自擲 dice20 決定起始位置。
- 每回合由躲藏者先行動，再由追捕者行動。
- 每位角色依序處理事件、移動及判定。
- 預設進行 10 回合，回合結束後躲藏者逃脫。

需要實作的特殊規則：

- 角色經過設施時的途經效果。
- 角色停留在設施格時的事件。
- 移動過程中的方向改變。
- 額外移動。
- 移動取消。
- 特殊傳送。
- 追捕與躲藏者相遇時的捕獲判定。
- 最大回合數變動。

## 7.2 多人模式

多人模式的行動順序：

1. 回合開始時，依照躲藏者目前所在格數字由小到大排列。
2. 同格躲藏者依照上回合先抵達者優先行動。
3. 每位躲藏者完成事件、移動及判定後，再輪到下一位。
4. 所有躲藏者完成行動後，由異常進行行動。

額外需要實作：

- 同格躲藏者的行動順序。
- 同格躲藏者的額外移動判定。
- 躲藏者被捕獲後的退場。
- 退場後其他躲藏者的選擇性移動。
- 異常的 coin 判定。
- 異常特殊結果。
- 最近躲藏者判定。
- 同距離時的順時鐘優先。
- 同位置捕獲最後抵達者。
- 接待廳返場規則。
- 每位躲藏者的返場次數限制。

多人模式的實作應與 1V1 模式共用底層地圖、移動及設施資料，但行動順序及捕獲邏輯應獨立處理。

# 十、開發注意事項

## 10.1 遊戲狀態必須統一

這是最重要的架構原則。

所有功能都應以同一份遊戲狀態為基礎：

- 地圖讀取角色位置。
- 事件生成器讀取目前角色及設施。
- 移動模組更新角色位置。
- 判定模組讀取角色及移動狀態。
- 文字生成器讀取已確認的結果。
- 存檔系統保存完整狀態。

避免各個功能各自維護一份資料，否則很容易發生地圖顯示與實際遊戲狀態不一致的問題。

## 10.2 預覽與確認必須分離

所有可能改變遊戲狀態的操作，都應先顯示預計結果。

例如：

- 預覽移動路徑。
- 預覽途經效果。
- 預覽事件結果。
- 預覽捕獲結果。

由主持人確認後，才正式更新遊戲狀態。

## 10.3 保留人工操作空間

這個工具的目的是減少主持人的計算及管理負擔，不是取代主持人的裁定權。

因此應保留：

- 手動調整角色位置。
- 手動修改骰子結果。
- 手動確認或取消特殊效果。
- 手動修正遊戲狀態。
- 手動接續遊戲。
- 撤銷上一個操作。

## 10.4 地圖與遊戲邏輯分離

地圖底圖只負責呈現。

遊戲位置、設施資料、角色狀態及移動路徑都應由 JavaScript 管理，再由地圖模組讀取並顯示。

未來即使更換地圖底圖，也不應影響遊戲規則及移動計算。

## 10.5 不要一次完成所有功能

建議先完成地圖及角色位置管理，再逐步加入遊戲邏輯。

尤其多人模式的行動順序、同格抵達順序及特殊捕獲判定，應等 1V1 核心流程穩定後再開發。

# 十二、最終專案目標

完成後的網站應是一個以主持人為中心的遊戲輔助工作台。

主持人只需要：

1. 在 Plurk 上進行遊戲及擲骰。
2. 將骰子結果輸入網站。
3. 由網站計算移動及遊戲判定。
4. 檢查生成的遊戲敘述。
5. 複製文字至 Plurk。
6. 匯出地圖圖片並發布。
7. 讓網站自動保存遊戲進度。

整個網站不需要玩家端介面，也不需要雲端資料庫。

**核心目標是：讓主持人能將注意力放在遊戲敘事與玩家互動，而不是反覆計算位置、確認規則及整理遊戲資訊。**
